## Context

TrustForge is presented as Hermes, an auditable market-analysis agent. The
competition requires each run to produce a report, Evidence list and execution
log that can be traced back to sources. Meeting requirements additionally call
out government announcements, crawler execution and source-level runtime.

## Delivered

- Five visible Hermes nodes: source ingestion, claim extraction, trust
  reasoning, evidence assembly and report delivery.
- A source-level `ingestion.source` event for official OHLCV, on-chain,
  government/regulatory, exchange, news and social sources. Each event records
  source name/kind, safe outcome, document count and milliseconds elapsed.
- A Hermes UI source execution table that exposes success, empty result or
  failure separately from the analysis nodes.
- Five-year OHLCV lineage on price Evidence: safe filename, SHA-256, complete
  coverage, row count and exact analysis window.
- A deterministic, original 240-case question bank: 60 multi-source, 60
  hypothesis-verification and 120 comparison cases. Coverage includes
  government/regulatory evidence, crawler/cache freshness, source conflicts,
  evidence gaps, risk and reversal conditions.
- `scripts/run_question_bank.py`, which validates report/Evidence/log fields
  and emits case outcomes plus end-to-end and per-source p50/p95 latency.
- GitHub CI runs a bounded 24-case offline gate and uploads the result artifact;
  release CD is gated by a version tag, GitHub production approval, backend/QA/
  frontend verification, then OIDC deployment through the existing EC2/SSM and
  nginx scripts.

## Historical Replay

- Scheduled prefetch creates point-in-time source archives for BTC/ETH/SOL/BNB/
  XRP before daily trust snapshots. Documents carry `published_at` (or explicit
  unknown), cache `fetched_at`, and archive `snapshot_at`.
- Formal replay only selects archives at or before `run_started_at`; missing
  historical data remains missing and is never reconstructed from current cache.
- `scripts/run_historical_replay.py` evaluates stored decisions against official
  OHLCV at T+1/T+7/T+14 and reports hit rate, directional return, drawdown and
  reliability bins. Current confidence remains information completeness until a
  separate historical calibrator passes a held-out evaluation.

## Hermes Self-Improvement And Skill Control

- Each autonomous cycle ends with `diagnose_improvement`, which converts durable
  scheduler failures, question-bank gaps, source latency and replay diagnostics
  into evidence-backed sandbox proposals.
- Hermes may automatically observe and propose, but may not automatically alter
  production code, Trust weights, models, prompts or completed formal reports.
- The deterministic core remains fixed: time boundary, Evidence/data lineage,
  Trust Layer, execution log and formal-run isolation. Evolvable outer skills
  include source, analysis, report, evaluation and improvement policies.
- Every outer skill revision follows append-only `stage -> approve -> active ->
  rollback`. Each record preserves hash, prior hash, validation evidence and
  reason. Rollback switches to an earlier approved revision without deleting the
  failed experiment.

## Outer Framework And Historical Backfill

Hermes evolves only its outer framework: source, retrieval, claim, reasoning,
report, evaluation, memory, experiment, operations and model-routing policies.
The time boundary, Evidence binding, deterministic Trust Layer and formal-run
isolation are immutable.

## 2026-07-16 Continuous Analysis And Question Memory

- Hermes now runs a durable five-stage SQLite pipeline continuously across the
  complete coin, analysis-mode and active-question matrix.
- Crawlers publish immutable snapshots. Work already running stays locked to its
  snapshot; a later data revision creates the next matrix without interrupting it.
- Active questions and user/Hermes dialogue are durable SQLite records.
- Question RAG retrieves similar historical questions, completed answers and
  run/snapshot lineage. Retrieved conclusions are marked non-evidentiary and do
  not become current Trust Evidence.
- Historical pipeline reliability, retry, latency and question-similarity
  measurements now feed the outer-framework diagnostic. It may create a sandbox
  proposal, but activation still requires replay evidence and human approval.
- UI ownership is explicit: left is dialogue/memory, center is the published
  snapshot, right is trust/evidence plus engine load, bottom is stage execution.

Historical work starts now rather than waiting five years. Backfilled records
must include provider, license, `published_at`, actual `retrieved_at` and a
content hash, and are labelled `backfilled_archive`. Daily replay selects only
records published on or before day T, then evaluates official OHLCV outcomes at
T+1, T+7 and T+14. A backfill never claims to know the historical fetch time.

## 2026-07-16 Upgrade Governance And Runtime Stabilization

- The upgrade control plane now registers 31 outer modules plus one independently
  versioned Trust Kernel package. The Trust Kernel remains release-locked and is
  never part of recursive or automatic outer-framework upgrades.
- Diagnostic proposals, adversarial LLM reviews, sandbox artifact hashes/results,
  and human approve/reject decisions are durable SQLite records.
- Only a `sandbox_passed` candidate may be approved. Approval remains distinct
  from activation and always reports `activated=false`; deployment still requires
  a reviewed branch, tests, PR, release and rollback record.
- Admin writes require the separate `X-Admin-Token`; public upgrade projection is
  read-only. Tokens never enter URLs, Wiki content or memory.
- Telemetry polling is serialized: each analysis-flow or journey request finishes
  before the next poll is scheduled, and unmount aborts the active request.
- Short-lived Web API `AnalysisFlow` objects explicitly close their SQLite
  connections. A live request-storm investigation reduced the backend from about
  674 stacked request threads to a stable two-thread idle state.
- Local `4174` frontend and `8799` backend run as launchd KeepAlive services.

## 2026-07-17 v0.16.0 Release Candidate

This release restores monotonic versioning after `v0.15.0` and packages the
completed Hermes data-foundation work as `v0.16.0`.

- Provider fetches are appended to immutable `source_events` before a valid
  latest-value cache may be replaced.
- Document, Evidence and Report payloads use versioned contracts with explicit
  compatibility checks; invalid payloads enter append-only quarantine.
- Snapshot, analysis job, stage and published-result lineage is durable and
  queryable. Completed results materialize point-in-time features atomically.
- Five-year OHLCV backfill and leakage-safe daily replay retain provider,
  licensing, event-time, availability-time and content-hash provenance.
- Hidden Hermes workspaces are suspended instead of continuing to render and
  poll beneath the active page, removing the history-page crash/flicker path.
- Branch audit found no active feature branch with commits missing from
  `develop`; obsolete release branches remain intentionally unmerged.

## Online Test Gate

Run online results only after a human refreshes AWS credentials and confirms
provider cost/cache settings:

```bash
python3 scripts/run_question_bank.py --online --all
```

Keep online results separate from the offline fixture report. A valid source
failure should remain visible in the log and report limits rather than being
silently hidden.

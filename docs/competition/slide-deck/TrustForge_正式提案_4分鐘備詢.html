答題節奏：第一句直接回答；第二句指出畫面、交付物或程式證據；被追問時再展開限制。不要把簡報重新講一遍。

十四題核心備詢

1. 你們自行訓練的是什麼模型？

我們自行訓練的是TrustForge信心校準模型，不是大型語言模型。它把分析當下的raw confidence與T+7等後續真實結果接合，再用Isotonic Regression校準成較符合歷史表現的信心。

calibration_model.py、modelhub_training.py、training JSONL與model artifact。

它不生成市場文章、不取代Bedrock，也不等於價格預測模型。

2. 為什麼不只使用AWS現成模型？

AWS基礎模型擅長語意理解與生成，但不知道TrustForge的Evidence契約、來源可靠度與信心定義。自有校準模型能針對任務修正過度自信、跟上市場變化，並累積來源可靠度資料護城河。

Bedrock負責extract／stance／narrative；Trust Layer與calibration_model負責信任計算與校準。

不是排斥AWS，而是把AWS基礎模型與自有任務模型放在不同責任層。

3. ModelHub和SageMaker有何不同？

兩者都實作TrainingBackend介面：觸發訓練、輪詢結果、下載產物。ModelHub以req_no呼叫訓練服務；Amazon SageMaker以Training Job執行，資料與artifact透過S3。

training_backend.py、modelhub_backend.py、modelhub_client.py、sagemaker_client.py。

正式競賽採AWS路徑。ModelHub已有weighted ECE改善門檻；SageMaker目前完成artifact驗證與人工核准，完整holdout ECE比較仍需補齊。

4. 自行訓練是否違反「僅限AWS基礎模型」？

不衝突。生成式AI基礎模型只使用Amazon Bedrock；自有校準模型是TrustForge的確定性信心映射，正式競賽可在允許的AWS EC2或SageMaker AI執行，不呼叫第三方生成模型。

Bedrock是唯一生成式模型入口；SageMakerBackend只負責校準訓練。

若主辦方解釋為所有模型都必須走AWS服務，我們就只啟用AWS訓練路徑，ModelHub僅作賽外治理參考。

5. 為什麼模型不能自動更新？

新資料可能污染、分布可能漂移，候選模型也可能退化。程式把automatic_apply固定為false、requires_human_approval固定為true；新版本必須通過資料Gate、產物驗證與人工審查。

modelhub_training.py、modelhub_submit.py、sagemaker_submit.py的candidate proposal。

持續學習是持續產生可審查候選，不是模型自行改寫正式系統。

6. 六類資料來源如何驗證？

市場行情以HOYA BIT／官方OHLCV為共同基準；鏈上、新聞、官方監管、社群及基本面資料各自保存來源身分、取得時間、引用片段與查詢條件。關鍵結論必須對應related_claim。

schema.py的Evidence欄位：source、fetched_at、content_reference、related_claim、source_url。

資料源失效或覆蓋不足會明示data mode與限制，不把cache／fixture說成即時資料。

7. 如何避免新聞重複計票？

系統先正規化來源身分，再用文本相似度與來源關係形成群組；交叉佐證只計真正獨立來源。Jaccard高相似群組會被標記，呈現可能的轉載或協同發文。

trust/scoring.py的Jaccard、union-find相似簇與independent_sources。

高相似不會一律自動扣分，因為合法聯播也可能相似；系統先透明標示，再決定是否計票。

8. Bedrock是否負責市場判斷？

不單獨負責。Bedrock可做主張抽取、有限立場分類與報告敘事；來源權重、獨立佐證、矛盾、校準與輸出契約由Trust Layer決定。報告必須以claim_id對應Evidence。

pipeline.py四步流程、bedrock.py、trust/kernel.py與Reasoning Provenance。

Bedrock未呼叫或失敗時，Execution Log必須標示offline／fallback，不能冒充模型成功。

9. API Key及AWS憑證如何保護？

長效憑證不得進Git；正式環境使用IAM Role與SSM Parameter Store。nginx以HTTPS對外，Python API僅監聽loopback；公開Evidence與Log只輸出必要欄位。

ssm_params.py、connector secret adapters、nginx設定與secret scan。

Workshop Access Code也屬機密，不會出現在簡報、Repo或公開紀錄。

10. 15分鐘內失敗怎麼處理？

每階段都受ExecutionLog剩餘時間與外部呼叫timeout控制。單一來源失敗可切換有時間戳的快取或明確降級；關鍵資料不足時降低信心或棄權。無法完成就保留失敗Log，不提交假成功。

execlog.py的remaining、pipeline timeout／fallback、connector cache的fetched_at。

原則上不以重新送出掩蓋第一次失敗；只有主辦環境問題才依規定申請重跑。

11. 四份交付物如何證明是真實執行？

四份檔案以同一個run_id與claim_id串接。Report的關鍵依據能回Evidence；Evidence保存來源與取得時間；Execution Log保存工具、資料模式、模型、成本與錯誤；Source／Config提供程式、設定、依賴鎖定與重現步驟。

report.md、evidence.json、execution_log.jsonl、GitHub Source／Config、artifact SHA-256。

不能只用漂亮畫面證明執行；評審應能完成Report→Evidence→Log→Source交叉抽查。

12. 「核心可替換」具體是什麼？

Trust Kernel只接收標準化Claim並輸出信任結果；資料來源、模型、快取、監控與預算控制透過Protocol介面接入，因此更換外部服務時不必改寫核心評分規則。

trust/kernel.py的KernelInput／KernelOutput／run_kernel，以及ports.py的ModelProvider、SourceProvider、CacheProvider、ObservabilityProvider與BudgetProvider。

目前kernel仍延遲載入scoring.py，架構測試將它列為待移除bridge；可以說已建立可替換邊界，不應說已百分之百完全解耦。

13. 鯨魚動態如何影響分析？

Whale Alert提供大額轉帳事件，Arkham補充實體與標籤歸因，Etherscan驗證鏈上交易，CoinMarketCap補充市值與流動性。這些資料會形成鏈上Evidence，與價格、新聞及其他來源交叉判讀。

ingestion/whale_trades.py、ingestion/etherscan.py、ingestion/cmc.py及test_whale_trades_arkham.py。

巨鯨轉入交易所不是必然看空，也不會直接變成買賣建議；若憑證或live來源未啟用，必須在Execution Log標示cache／fixture／unavailable。

14. 你們是否已完成碳盤查？Trust Kernel真的低於1秒嗎？

目前沒有宣稱完成正式碳盤查，也沒有把低於1秒當成已驗證SLA。我們能證明的是核心評分採本機記憶體計算、正式路徑避免不必要的LLM呼叫，並記錄Bedrock token、成本、預算與快取使用。

trust/kernel.py的offline核心路徑、bedrock.py的token usage、budget_guard.py及ingestion/cache.py。

沒有完整benchmark前不報固定延遲；沒有排放係數、組織邊界與查證流程前，不使用「ISO 14064對齊」或「已完成碳盤查」。

延伸高機率追問

TrustScore能預測漲跌嗎？
不能這樣宣稱。它衡量資訊完整度、可溯源性與佐證品質，不提供報酬保證。
來源互相矛盾怎麼辦？
保留正反證據、降低信心並列出could_flip，不把矛盾平均掉。
HOYA BIT如何導入？
第一步在市場資訊頁加入完整度、Evidence與反轉條件；第二步累積來源歷史與校準資料；第三步以Trust Layer API整合研究工具。
最大限制是什麼？
正式入口與外部資料受現場權限、網路與契約影響；SageMaker完整ECE比較尚未與ModelHub完全對齊。

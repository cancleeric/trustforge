## 1. 一句話定義

> **TrustForge 不「給你一個答案」，而是讓證據上法庭——起訴、辯護、合議，輸出「判決書 + 不同意見書」。**

創意不在多開幾個 AI，而在**重新框住既有能力**：把我方已經在做的「正反方證據 + 反方低信任證據 + 限制複審」，重新敘事成一場**可觀看的正當程序（due process）**。信任的本質就是「經得起交叉詰問」——這是把主題「信任提煉」做到字面。

---

## 2. 三個角色 ↔ 既有 codebase（不新增模型呼叫）

| 法庭角色 | 做什麼 | 對應既有實作（重塑，非新建） |
|---------|--------|---------------------------|
| **起訴方 / 辯護方**（多方 vs 空方） | 各自舉出最強證據 | `Report.hypothesis_ledger`（pro/con 證據帳本，綁定 Evidence 索引，`orchestrator.build_report` 已填）；`Report.contrarian`（反方低信任證據） |
| **證據交叉詰問** | 揭露來源自我矛盾、跨源背離 | `detect_source_self_contradiction`、`cross_source_signal["stance_pairs"]`（同議題跨源立場對） |
| **合議庭 / 判決** | 加權裁決、給主結論 | 既有 `build_report` 的信任加權融合 + `Report.market_judgment` / `confidence`（W4 校準信心） |
| **不同意見書（dissent）** | 明列什麼會推翻判決 | `Report.could_flip`（可推翻條件）、`Report.limits`（限制） |
| **書記官（行文）** | 只把裁決寫成人話 | Bedrock（既有唯一模型入口 `bedrock.py`）——**只行文、不判斷** |

**關鍵**：judge（加權裁決）是**確定性 pipeline** 算的、clerk（Bedrock）只行文——這正是反作弊鐵則的活教材，且**評審親眼看到判斷不是抄第三方結論**。

---

## 3. 輕量版怎麼「輕」（成本紀律）

- **不新增審判用 Bedrock agent**。正式 15 分鐘內模型呼叫次數維持現狀（既有 3 次推理 + 選用 Step4）。
- 「起訴/辯護」用的是**已抽取、已評分的證據**重新分組呈現，不再各跑一次 LLM。
- 「合議」沿用既有 Step4 限制複審那一次（預算剩 >60s 才觸發），**把唱反調併進去**——一次呼叫同時產出判決措辭 + 不同意見書。
- 若預算不足 → 降級成純結構化輸出（judgment + pro/con + dissent 清單，無潤飾行文），仍完整、仍對題。

## 4. 呈現（把「程序」變成可觀看的信任證明）

**報告頂部「判決書」區塊：**
```
┌─ 判決 · SOL｜多源整合 ───────────────────────────┐
│  主結論：偏空（校準信心 0.42）                      │
│                                                    │
│  起訴（偏空）  ●●●  3 條獨立高信任證據              │
│     ├ 鏈上：交易所淨流入 +2.1% [claim_12] trust .81 │
│     └ …                                            │
│  辯護（偏多）  ●○○  1 條，且 2 條同文回音已剔除      │
│     └ 社群情緒高漲 [claim_31] trust .34（低）        │
│                                                    │
│  交叉詰問：來源 A 前後自我矛盾（見 [claim_08/22]）   │
│                                                    │
│  ── 不同意見書 ──                                   │
│  若 24h 交易所淨流入轉負 → 判決應改中性              │
└────────────────────────────────────────────────────┘
```
- pro/con 用**信任加權的「●」量**表達強弱，不是條數（回音已剔除，呼應 ①信任赤字的獨立性）。
- 「書記官行文 vs pipeline 判斷」可用不同樣式標示（延伸 CEO 加碼「判斷來源分離視覺」，claim_id 已存在）。

## 5. 對應評分項

| 評分項 | 玻璃箱法庭如何得分 |
|--------|------------------|
| **30% 主題** | 正當程序 = 信任提煉的字面實作；正反方 + 交叉詰問 + 不同意見書一次命中「矛盾處理 / 不確定性 / 限制說明」 |
| **25% 技術** | 展示清晰 agent 編排（judge=pipeline、clerk=LLM 職責分離）；**反作弊鐵則的可展示證明** |
| **15% 創意** | 「AI 判決書 + 不同意見書」的敘事，評審沒看過別隊這樣呈現 |
| **20% 商業** | 交易者拿到的不是黑箱結論，是「可上訴、知道何時失效」的判斷 |
| **10% 完成** | 全部沿用既有 schema 欄位輸出，穩定可序列化 |

## 7. 已知限制（誠實登錄）
- 「起訴/辯護」品質取決於證據抽取品質；證據稀薄時法庭要誠實顯示「證據不足以成案」（沿用三態合約），不硬演一場戲。
- 不同意見書的 could_flip 必須是**可觀測條件**（如鏈上數值門檻），不可是空泛「若情勢改變」。
- 輕量版不做真多 agent 對辯，是「單次合議 + 結構化重組」——對外據實稱「可解釋的正當程序」，不誇稱「多智能體法庭」。

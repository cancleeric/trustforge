# TrustForge 信任分數可解釋性文件（Trust Explainability）

> 本文件說明 TrustForge 的可信度如何計算、資料從哪來、為什麼可信。
> 目的：讓主辦方、評審、使用者能理解並解釋我們的信任分數。

---

## 1. 信任分數是什麼？

TrustForge 的信任分數（TrustScore）**不是價格預測**，是一條主張（claim）的**資訊完整度指標**——衡量「這條資訊有多少可回溯的證據支撐」。

分數範圍：0–1（對外顯示為 0–100）

| 區間 | 含義 | 使用者應如何解讀 |
|------|------|----------------|
| 0.8–1.0 | 高完整度 | 多個獨立來源交叉佐證，溯源鏈完整 |
| 0.5–0.79 | 中完整度 | 有佐證但來源數量或獨立性有限 |
| 0.3–0.49 | 低完整度 | 僅單一來源或來源信譽不足 |
| 0–0.29 | 極低/棄權 | 資料嚴重不足或疑似操縱，建議不採信 |

**⚠️ 重要聲明：** 信任分數高不代表「會漲」或「值得買」，只代表「支撐這條結論的證據比較完整」。

## 2. TrustScore 四維計算公式

```
TrustScore = w₁ × SourceReputation
           + w₂ × CrossSourceCorroboration
           + w₃ × RecencyDecay
           − w₄ × ManipulationPenalty
```

### 各維度詳細說明

| 維度 | 權重 | 計算方式 | 為什麼這樣設計 |
|------|------|---------|--------------|
| **SourceReputation（來源信譽）** | w₁=0.30 | 預設信譽表 + 歷史準確率追蹤 | 官方公告 > 主流媒體 > 社群 KOL > 匿名帳號 |
| **CrossSourceCorroboration（交叉佐證）** | w₂=0.35 | 同一主張被多少「獨立」來源佐證 | 獨立來源越多越可信（去重後計算，避免回音室） |
| **RecencyDecay（時效衰減）** | w₃=0.20 | 資料取得時間距今的指數衰減 | 加密市場變化快，72 小時以上的資訊信譽打折 |
| **ManipulationPenalty（操縱懲罰）** | w₄=0.15 | 偵測喊單語意、bot 行為模式 | 匿名社群的協同發文、喊單語法觸發懲罰扣分 |

## 3. 資料來源清單（每類的可信度理由）

### 資料分類與信譽預設值

| 來源類型 | 具體來源 | 預設信譽 | 為什麼給這個分數 |
|---------|---------|---------|----------------|
| **官方 OHLCV** | 主辦方提供 5 年 Daily CSV | 0.95 | 主辦方直接提供，無中間人篡改風險 |
| **HOYA BIT 行情** | HOYA BIT API（ticker + depth） | 0.85 | 命題方自有數據，直接整合 |
| **鏈上數據** | CoinGlass（交易所流入流出）、blockchain.info | 0.80 | 客觀鏈上記錄，無人為敘事偏差 |
| **主流新聞** | CoinDesk、Decrypt、CryptoPanic RSS | 0.60 | 有編輯審核，但可能有贊助商偏見 |
| **監管公告** | SEC RSS、各國金管機構公告 | 0.90 | 官方法規文件，極少虛假 |
| **社群輿情** | Reddit r/Bitcoin r/solana | 0.35 | 匿名為主，易受操縱，僅作為情緒指標 |
| **社群 KOL** | X/Twitter 認證帳號 | 0.40 | 有公開身分但利益衝突未揭露 |

### 為什麼「鏈上 > 新聞 > 社群」？

1. **鏈上數據是客觀事實**——交易紀錄無法偽造（需 51% 攻擊），所以信譽最高
2. **新聞有編輯流程**——但可能受廣告商影響，所以中等
3. **社群是主觀意見**——匿名、易操縱、回音室效應強，所以最低

## 4. 可信度為什麼可信？（三重保障）

### 保障一：來源透明可回溯

每條主張都帶完整溯源：
```json
{
  "claim_id": "c-2026-08-01-sol-0012",
  "claim_text": "SOL 交易所淨流出 48,000 SOL（24h）",
  "source": "coinglass-api",
  "source_url": "https://www.coinglass.com/...",
  "fetched_at": "2026-08-01T09:23:00Z",
  "content_reference": "SOL exchange netflow -48,000 SOL, 2026-07-29~2026-08-01",
  "trust_score": 0.87,
  "trust_breakdown": {
    "source_reputation": 0.80,
    "cross_corroboration": 0.92,
    "recency": 0.95,
    "manipulation_penalty": 0.0
  }
}
```

使用者可以：
- 點開 `source_url` 自己驗證
- 看 `trust_breakdown` 知道哪個維度拉高/拉低了分數
- 用 `fetched_at` 判斷資料新鮮度

### 保障二：反作弊架構（LLM 不能編造）

- LLM（Bedrock）**只負責行文**，不負責判斷
- 判斷結構由 Trust Layer（純演算法）產生
- LLM 收到的是已加權的 TrustedBrief，只能引用 `claim_id`
- 報告裡每句標明「pipeline 判斷」vs「LLM 行文」

→ **LLM 幻覺不會汙染信任分數**

### 保障三：矛盾不隱藏

- 如果來源互相矛盾（鏈上看空 vs 社群看多），兩邊都會呈現
- 信任分數會反映矛盾：佐證分（CrossSourceCorroboration）自動降低
- 報告的「反方證據」區塊保證存在

## 5. 信任分數的已知限制（誠實揭露）

| 限制 | 說明 | 我們怎麼處理 |
|------|------|------------|
| 不是預測指標 | AUC≈0.49（近隨機）用於價格預測 | 明確定位為「資訊完整度」非「預測準確度」 |
| 來源信譽是預設值 | 初始信譽基於經驗判斷 | 長期目標：歷史表現動態更新信譽 |
| 冷門幣資料稀少 | BNB/XRP 新聞量可能很低 | 資料不足時誠實標「資訊完整度：低」 |
| 社群操縱偵測非 100% | 新型 bot 可能繞過 | 標記為「疑似」而非「確認」，保留在報告供人判斷 |
| 即時性窗口有限 | API 免費方案有 rate limit | 失敗來源標明在 `report.limits` |

## 6. 使用者如何驗證信任分數？

### 快速驗證三步驟

1. **看 Evidence List**：每條結論旁邊有 `[E1][E2]` 編號，點開看原始來源
2. **看 Trust Breakdown**：四維分數哪個高哪個低，判斷是否合理
3. **看矛盾帳本**：是否有反方證據被列出，如果有，信任分數是否因此降低

### 評審抽查指南

評審可以：
1. 隨機選一條高分主張 → 點開 source_url → 確認內容存在且匹配
2. 隨機選一條低分主張 → 看是哪個維度拉低 → 判斷是否合理
3. 查看「操縱旗標」的主張 → 看標記理由 → 是否確實像喊單

## Slide 2：我們是什麼（0:45–1:30）

### TrustForge = 多源資訊的「信源熔爐」

**一句話：**
> Incumbent 給你答案與分數；TrustForge 給你**答案背後每一條可點回原始來源的證據鏈，以及多源背離偵測**。

| 一般 Crypto AI Agent | TrustForge |
|---|---|
| 多源 → 直接丟 LLM 摘要 | 多源 → **逐條主張信任評分** → 加權後才進 LLM |
| 來源不分等級 | **信譽 × 交叉佐證 × 時效** 三維評分 |
| 結論無溯源 | 每個結論帶 **provenance（溯源鏈）** |
| 一句話結論 | **資訊完整度分級 + 反方證據 + 溯源鏈** |

> 我們交付的不是「一個答案」，而是「一個你能查證的答案」。

## Slide 3：核心技術 — Trust Layer 信任層（1:30–2:30）

### 三層 Pipeline 架構

```
┌─────────────────┐     ┌──────────────────────┐     ┌────────────────────┐
│ Layer 1 多源輸入  │     │ Layer 2 信任提煉(核心) │     │ Layer 3 Agent 輸出  │
│                 │     │                      │     │                    │
│ • 新聞/RSS       │     │ 1. 主張抽取(Bedrock)   │     │ • 帶 claim_id 溯源   │
│ • 社群/X/Reddit  │ ──▶ │ 2. 來源信譽評分        │ ──▶ │ • 信任加權融合        │
│ • 鏈上 on-chain  │     │ 3. 交叉佐證           │     │ • 反方證據 / 限制說明  │
│ • OHLCV 行情     │     │ 4. 時效衰減           │     │ • 資訊完整度分級      │
│ • 監管/公告      │     │ ⇒ TrustScore/claim   │     │                    │
└─────────────────┘     └──────────────────────┘     └────────────────────┘
```

### TrustScore 四維公式

```
TrustScore = w_src × SourceReputation
           + w_corr × CrossSourceCorroboration
           + w_rec × RecencyDecay
           − w_manip × ManipulationPenalty
```

### 防禦 Cross-Source Conflation（arXiv:2606.18037）
- 業界忽略的失效模式：一條 claim 被支持，卻歸因到**錯誤來源**
- 我方 Evidence Trail：每條結論追溯原始來源、標記矛盾來源

## Slide 4：招牌四武器 — 創意差異化（2:30–3:30）

### ① 反事實 A/B 對照
關掉信任層的 naive RAG vs TrustForge → naive 被假新聞帶偏、我方壓掉了

### ② 來源獨立性圖譜
N 篇「新聞」塌縮成 K 個真獨立源 → 「去重前 11 篇同文，去重後僅 3 獨立源」

### ③ 矛盾帳本
跨源分歧顯性列出（鏈上偏空 vs 社群偏多）+ 推理「為何這樣加權」

### ④ 負空間情報
監管 0 事件、巨鯨異常安靜 → 把缺席當情報，不是略過
- 標記「未觀察到 ≠ 不存在」

### 🎯 判斷來源分離視覺（Reasoning Provenance）
報告每句標明「pipeline 判斷（帶 claim_id）」vs「LLM 純行文串接」
→ 評審親眼看到**無任何第三方結論滲入** = 反作弊合規的視覺化證明

## Slide 9：可信度怎麼來的（給評審/主辦方/使用者解釋用）

### TrustScore 四維拆解 — 每一層都透明

| 維度 | 權重 | 資料從哪來 | 為什麼可信 |
|------|------|-----------|-----------|
| **來源信譽** | 30% | 預設信譽表（官方 0.90 > 鏈上 0.80 > 新聞 0.60 > 社群 0.35） | 基於可驗證的客觀性層級排序 |
| **交叉佐證** | 35% | 同一主張被多少「去重後獨立」來源佐證 | 獨立來源越多 = 不是回音室 |
| **時效衰減** | 20% | 資料取得時間距今的指數衰減 | 加密市場變化快，舊資料打折 |
| **操縱懲罰** | 15% | 喊單語意偵測、bot 協同發文偵測 | 匿名 bot 放大的訊號不可信 |

### 使用者怎麼驗證？
1. 點 Evidence → 看原始 URL，自己確認內容存在
2. 看 Trust Breakdown → 知道哪個維度高/低
3. 看矛盾帳本 → 確認反方證據有被列出

### 與實際可信度一致的保證
- 分數高 ≠ 會漲，只代表「證據比較完整」
- 資料不足時自動降為「資訊完整度：低」，不虛報
- 來源失敗時標明在限制欄位，不假裝沒問題

## Slide 12：資安設計

### 四層縱深防禦

| 層級 | 防禦重點 | 具體措施 |
|------|---------|---------|
| **基礎設施** | 最小權限 | IAM 只給 bedrock:InvokeModel + s3:GetObject + SSMCore |
| **網路** | 加密傳輸 | TLS 1.2+ / HSTS / 後端只聽 127.0.0.1 |
| **應用** | 防濫用 | Token Gate / Dedup / 輸入驗證 |
| **資料** | 零個資 | 不蒐集帳號、IP、持倉，不連接交易所帳戶 |

### 關鍵安全設計
- 🔒 **EC2 無 SSH key** — 全走 SSM，不可能被暴力破解
- 🔒 **Bedrock Token Gate** — 公開 URL 無 token 無法觸發 AI
- 🔒 **LLM 不能自創結論** — 只引用 pipeline 驗證過的 claim_id
- 🔒 **API key 不入版控** — pre-push hook + .gitignore
- 🔒 **SG 只開 80/443** — 無 SSH、無 DB port
